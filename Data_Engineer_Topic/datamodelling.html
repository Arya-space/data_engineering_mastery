Section 01

What is Data Modelling?

Data modelling is the process of designing how data is structured, stored, and related — before you write a single line of pipeline code. It's the blueprint everything else is built on.

💡 Bad data model = every query is slow, every report is wrong, every new feature is painful. A good model makes everything downstream easier.

// Three levels of modelling

Conceptual

What entities exist and how they relate. No columns, no types — just boxes and lines. For business stakeholders.

Customer → Order → Product
Logical

Adds attributes and relationships. Still not tied to a specific database. For data architects.

Customer(id, name, email)
Physical

Actual DDL — CREATE TABLE, data types, indexes. Tied to a specific engine. For engineers.

VARCHAR(100), INT, DATE

Section 03

OLTP vs OLAP

This is the most important distinction in data modelling. It determines everything — schema type, normalization level, indexing strategy.

OLTP — Online Transaction Processing

Optimized for writes. Many small, fast transactions. Powers your app.

PropertyValue
OperationsINSERT, UPDATE, DELETE
Query sizeSmall (1 row)
SchemaNormalized (3NF)
UsersApp, customers
ExamplePlace an order
OLAP — Online Analytical Processing

Optimized for reads. Few large queries across millions of rows. Powers analytics.

PropertyValue
OperationsSELECT (aggregations)
Query sizeLarge (millions of rows)
SchemaDenormalized (Star)
UsersAnalysts, BI tools
ExampleRevenue by region last quarter
✓ Rule of thumb: OLTP = source systems (Postgres app DB). OLAP = your data warehouse (Snowflake, BigQuery). Data engineers move data from OLTP → OLAP.

Section 06

Denormalization & Flattening

Normalization is great for transactions. But for analytics, joins are expensive. Denormalization deliberately re-introduces redundancy to speed up reads.

Denormalization

Combine multiple normalized tables back into fewer wider tables. Trade storage for query speed.

-- Instead of joining 3 tables every time:
SELECT o.order_id, c.name, p.name
FROM orders o
JOIN customers c ON o.cust_id = c.id
JOIN products p ON o.prod_id = p.id

-- One wide table:
SELECT order_id, customer_name, product_name
FROM fact_orders
Flattening

Convert nested structures (JSON, arrays) into flat columns. Required for columnar warehouses.

-- Nested JSON (from MongoDB/API):
{
  "order_id": 1001,
  "customer": {
    "name": "Alice",
    "city": "London"
  }
}

-- Flattened:
order_id | customer_name | customer_city
1001     | Alice         | London
💡 When to flatten? Always when loading into Snowflake, BigQuery, or Redshift. Columnar engines don't handle nested structures well — flatten first in your transformation layer (dbt or Spark).
Section 07

Grain Definition

Grain is the most important decision in data modelling. It answers: "What does one row in this table represent?"

⚠ If you get grain wrong, every metric built on top of it will be wrong. Define grain before you design any columns.

// Grain examples

TableGrain (one row = ?)What it means
fact_ordersOne order line itemIf an order has 3 products → 3 rows
fact_sessionsOne web session per userEach visit = 1 row
fact_paymentsOne payment transactionEach payment attempt = 1 row
dim_customersOne customer (current version)One row per unique customer

// The grain question to always ask

Before designing any fact table, ask: "At what level of detail do we need to answer business questions?"

Too granular = too much storage, slow queries.
Too coarse = can't answer detailed questions later.

Section 10

Fact Table Types

Not all fact tables are the same. The type of fact table you choose determines the grain, how rows accumulate over time, and what kinds of queries are possible. This is one of the most common interview topics in dimensional modelling.

Transaction Fact

One row per discrete event or transaction. The most common type. Row is inserted when the event happens and never updated. Append-only.

Examples: each sale, each click, each payment, each order line item.

Simplest to build Append-only Most granular

Periodic Snapshot Fact

One row per entity per time period — regardless of whether anything happened. Captures the state at a point in time. Rows are inserted on a schedule (daily, weekly, monthly).

Examples: account balance at end of day, inventory level each week, headcount each month.

Section 11

Dimension Types

Dimensions come in several specialised types beyond the basic customer or product dimension. Understanding these is what separates a junior modeller from a senior one — they come up constantly in Kimball-style design.

Conformed Dimension

A dimension shared across multiple fact tables with identical meaning. dim_date, dim_customer, dim_product used by both fact_sales and fact_returns are conformed. Enables cross-process analysis without data discrepancy.

Why it matters: if Sales and Finance use different dim_customer tables with different customer counts, the numbers will never agree.

Enables drill-across queriesSingle source of truth
Role-Playing Dimension

The same physical dimension used multiple times in the same fact table for different purposes. dim_date appears as order_date, ship_date, and delivery_date — three different roles, one table.

Implementation: create views or aliases (vw_order_date, vw_ship_date) pointing to the same dim_date table. Do not duplicate the table.

Views / aliasesNo duplication
Junk Dimension

A catch-all dimension that consolidates low-cardinality flags and indicators that don't belong in any natural dimension. Instead of 6 boolean columns on the fact table, create one junk dimension with all combinations.

Example: is_promotional, is_online, is_returned, payment_method, channel — all combined into dim_transaction_type.

Cleans up fact tableLow cardinality flags
Degenerate Dimension

A dimension attribute that lives directly on the fact table with no separate dimension table — because it has no other attributes. Order number, invoice number, ticket number are classic examples.

No separate dim table exists because there's nothing else to say about it — just the key itself used for grouping and filtering.

No separate tableKeeps model lean
Slowly Changing Dimension (SCD)

A dimension where attribute values change over time and you need to decide whether to overwrite (Type 1), track history (Type 2), or store both old and new (Type 3). The most important dimension concept in practice.

Full coverage in the dedicated SCD module — including DDL, DML, dbt snapshots, and a SQL playground.

History tracking→ SCD Module
Outrigger Dimension

A dimension that references another dimension — a secondary dimension hanging off a primary one. dim_product references dim_brand. Use sparingly — it adds joins and complexity. Usually better to flatten the attributes into the primary dimension.

Avoid unless the referenced dimension is shared with other primary dimensions — otherwise just denormalise.

Adds join complexityUse sparingly

Section 12

dbt Modelling Conventions

dbt has established a standard layer naming convention that maps directly to the Medallion architecture. Following it makes your project navigable for any data engineer who joins the team — it's become the industry default.

✓ The convention in one line: sources → staging → intermediate → marts. Each layer has a specific purpose, materialisation strategy, and naming pattern. Break the convention and the model becomes hard for others to understand.
Source (not a dbt model)

Raw tables from source systems declared in sources.yml. Not transformed — just referenced. Gives you source freshness checks and lineage tracking from the very start of the DAG.

# sources.yml
sources:
  - name: raw_postgres
    tables:
      - name: orders
      - name: customers
Declared not builtFreshness checks
Staging (stg_)

One-to-one with source tables. Clean but don't join. Rename columns to standard naming conventions, cast data types, apply basic filters, coalesce nulls. Nothing business-logic-specific here.

-- models/staging/stg_orders.sql
SELECT
  id            AS order_id,
  customer_id,
  created_at    AS ordered_at,
  status::text  AS order_status,
  amount / 100.0 AS amount_usd
FROM {{ source('raw_postgres','orders') }}
1:1 with sourceNo joinsMaterialise: view
Intermediate (int_)

Business logic that doesn't belong in staging or marts. Joins between staging models, deduplication, complex transformations, pivots. Not exposed to end users — building blocks only.

-- models/intermediate/int_orders_with_customers.sql
SELECT
  o.order_id,
  o.ordered_at,
  o.amount_usd,
  c.customer_name,
  c.customer_segment
FROM {{ ref('stg_orders') }} o
LEFT JOIN {{ ref('stg_customers') }} c
  ON o.customer_id = c.customer_id
Joins allowedNot user-facingMaterialise: view or ephemeral
Marts (fct_ / dim_)

Business-facing output. Fact tables (fct_) and dimension tables (dim_) that analysts and BI tools query directly. Optimised for read performance. Well-documented. This is the Gold layer.

-- models/marts/fct_orders.sql
SELECT
  order_id,
  ordered_at,
  customer_id,
  amount_usd,
  DATEDIFF('day', ordered_at, shipped_at)
    AS days_to_ship
FROM {{ ref('int_orders_with_customers') }}

-- models/marts/dim_customers.sql
SELECT
  customer_id,
  customer_name,
  customer_segment,
  first_order_at,
  lifetime_orders
FROM {{ ref('int_customer_summary') }}
User-facingfct_ and dim_ prefixMaterialise: table
