Section 01

Why Streaming is 10x Harder

Batch processing has a simple mental model: data is finite, you process it, you're done. Streaming breaks every one of those assumptions.

Data is infinite

A streaming pipeline never "finishes". Events keep arriving. You must process them in bounded windows — otherwise you can never produce an output.

Events arrive out of order

A mobile event created at 10:00am might arrive at your pipeline at 10:45am due to network issues. How do you aggregate "events from 10am–11am" when some arrive late?

Failures must be handled exactly

If your pipeline crashes and restarts mid-stream, does every event get processed exactly once? Or might some be skipped (at-most-once) or duplicated (at-least-once)?

ProblemBatch solutionStreaming solutionWhy it's harder in streaming
Process bounded dataRead the whole file/tableWindows — tumbling, sliding, sessionYou must choose a window strategy and live with its trade-offs
Handle out-of-order dataSort the file firstWatermarks + grace periodsYou must decide when to "close" a window and emit results
Fault toleranceRe-run the job from startCheckpointing + idempotent writesMust checkpoint state continuously without impacting throughput
Join two datasetsJOIN in SQL — trivialStream-stream join with time boundsBoth streams are infinite — you need a time window to bound the join
AggregationsGROUP BY — trivialStateful aggregation per windowState must be stored in a state backend (RocksDB) and checkpointed
⚠ The rule: Only use true streaming when sub-minute latency is a hard, non-negotiable business requirement. For everything else — fraud detection, live inventory, real-time alerts — streaming is justified. For "near real-time dashboards", micro-batch (5-15 min) is almost always the right answer and 10x simpler to operate.

Partitions are the key to Kafka's scalability. A topic with N partitions can be consumed by up to N consumers in parallel — each consumer owns one or more partitions.

⚡ Partition key determines routing. When a producer sends a message with a key (e.g. user_id), Kafka hashes the key to choose the partition. Same key always goes to the same partition — guaranteeing order for that key.
DecisionImpactRule of thumb
Number of partitionsMax parallelism = max consumers. More partitions = more overhead on broker.Start with 6-12 partitions per topic. Scale up if consumer lag grows.
Partition key choiceDetermines which partition a message lands on. Same key = same partition = ordered.Use the entity key (user_id, order_id). Never use a random key if order matters.
No partition key (null)Messages are distributed round-robin across partitions. No ordering guarantee.Use when order doesn't matter and you want maximum throughput.
Hot partitionsOne key generates 90% of traffic — that partition's consumer is overwhelmed.Add a salt suffix to the key (user_id + random 0-9) to spread load. Lose strict ordering.
⚠ You cannot reduce the number of partitions without deleting and recreating the topic. Over-partition rather than under-partition — it's easier to add consumers than to repartition.

A consumer group is a set of consumers that together consume all partitions of a topic. Each partition is assigned to exactly one consumer in the group at a time — guaranteeing that each message is processed by exactly one consumer in the group.

Scaling with consumer groups

3 partitions + 3 consumers in group = each consumer reads 1 partition. Adding a 4th consumer? It sits idle — more consumers than partitions is wasteful. Max parallelism = number of partitions.

Multiple consumer groups

Two separate services can each have their own consumer group on the same topic. Each group tracks its own offsets independently. Analytics pipeline and fraud detection service both read the same topic — completely independently.

ScenarioWhat happens
Consumer crashesKafka detects via heartbeat timeout. Triggers rebalance — partitions redistributed to remaining consumers in group.
Consumer addedRebalance triggered. Partitions redistributed to include new consumer. Brief pause in processing during rebalance.
Consumer lags behindConsumer offset falls behind the producer. If lag grows past retention period, messages are lost.
Reset to earliest offsetConsumer group replays all messages from the beginning of the topic — up to retention limit.
Commit offset manuallyConsumer marks a specific offset as "processed". On restart, resumes from that offset.

Kafka is not a message queue that deletes messages after consumption. Messages are retained for a configurable period — regardless of whether they've been consumed. This enables multiple consumers and replay.

Retention policyHow it worksUse case
Time-based (default)Delete messages older than N days (default: 7 days)Most streaming pipelines — keep last week for replay
Size-basedDelete oldest messages when topic exceeds N GBHigh-volume topics where time-based retention would be too large
Log compactionKeep only the latest message per key — older versions of same key are deletedDatabase changelog topics — only need latest state per entity
Infinite retentionNever delete. Topic grows forever.Kappa architecture event log — replay entire history
✓ Kappa architecture relies on long retention. If you set Kafka retention to 90 days, you can always replay 90 days of history — this replaces the batch layer. The trade-off is storage cost scales with retention × event volume.
Section 03

Delivery Semantics

One of the most important and most misunderstood concepts in streaming. The delivery guarantee determines what happens when failures occur — and every streaming system makes a trade-off between correctness and performance.

At-most-once

Messages are delivered zero or one times. If the consumer crashes after receiving but before processing, the message is lost — the offset was already committed.

commit offset → process message
Highest throughput Data loss possible

Use for: metrics, analytics where occasional loss is acceptable. Never for payments or fraud.

At-least-once

Messages are delivered one or more times. If the consumer crashes after processing but before committing the offset, the message is redelivered on restart — causing a duplicate.

process message → commit offset
No data loss Duplicates possible

Use for: most pipelines. Handle duplicates downstream with deduplication logic.

Exactly-once

Messages are delivered exactly one time. No loss. No duplicates. Achieved through idempotent producers + transactional APIs + atomic offset commit + write in the same transaction.

atomic: process + commit offset
No loss, no duplicates Lower throughput Complex setup

Use for: financial transactions, fraud detection, any pipeline where duplicates cause business impact.

// How exactly-once actually works

Exactly-once is not magic — it requires three components working together:

ComponentWhat it doesHow
Idempotent producerEnsures a message is written to Kafka exactly once even if the producer retriesEach message has a producer ID + sequence number. Kafka broker deduplicates retries.
Transactional producerWrites to multiple partitions and topics atomically — all succeed or all failProducer begins transaction, writes messages, commits. Consumers see all or nothing.
read_committed consumerConsumers only see messages from committed transactionsSet isolation.level=read_committed. Uncommitted messages are invisible.
 
// Exactly-once producer setup (Java)
props.put("enable.idempotence", "true");
props.put("transactional.id", "my-transactional-id");
props.put("acks", "all");  // wait for all replicas

producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord("topic", key, value));
producer.sendOffsetsToTransaction(offsets, groupMetadata);
producer.commitTransaction();  // atomic: message + offset commit

Section 04

Windowing

Windows turn an infinite stream into finite, bounded sets of events that can be aggregated. The window strategy you choose determines what questions you can answer and what trade-offs you accept.

Tumbling windows are fixed-size, non-overlapping windows. Every event belongs to exactly one window. The simplest window type.

Tumbling window — 10 min size
When to use

Hourly sales totals. Daily active users. Per-minute request counts. Any "how many X in this time period" question where periods don't overlap.

Trade-off

An event at 10:59 and an event at 11:01 are in different windows — even though they're 2 minutes apart. Edge events near window boundaries can appear artificially separated.

-- Flink SQL: tumbling window
SELECT
  user_id,
  TUMBLE_START(event_time, INTERVAL '10' MINUTE) AS window_start,
  COUNT(*) AS event_count
FROM user_events
GROUP BY
  user_id,
  TUMBLE(event_time, INTERVAL '10' MINUTE)

Sliding windows have a fixed size but move by a slide interval. Windows overlap — an event can appear in multiple windows. Gives a rolling/moving average effect.

Sliding window — 10 min size, 5 min slide
When to use

Rolling 5-minute fraud score. Moving average error rate. "How many requests in the last 10 minutes?" updated every 5 minutes. Any rolling metric.

Trade-off

Events are processed multiple times (once per window they appear in). More compute than tumbling. If slide < size, windows overlap. If slide = size, it degenerates to tumbling.

-- Flink SQL: sliding window (HOP)
SELECT
  user_id,
  HOP_START(event_time, INTERVAL '5' MINUTE, INTERVAL '10' MINUTE),
  COUNT(*) AS event_count
FROM user_events
GROUP BY
  user_id,
  HOP(event_time, INTERVAL '5' MINUTE, INTERVAL '10' MINUTE)

Session windows are dynamic-size windows that close after a gap of inactivity. No fixed size — the window grows as long as events keep arriving within the gap timeout.

Session window — 5 min inactivity gap
When to use

User session analysis — group all user activity until 30 min of inactivity. Shopping cart events. Support ticket interactions. Any "burst of activity" pattern.

Trade-off

Sessions are per-key (per user). The system must maintain state for every active user — memory grows with number of active sessions. Must choose gap duration carefully.

-- Flink SQL: session window
SELECT
  user_id,
  SESSION_START(event_time, INTERVAL '5' MINUTE) AS session_start,
  SESSION_END(event_time, INTERVAL '5' MINUTE) AS session_end,
  COUNT(*) AS events_in_session
FROM user_events
GROUP BY
  user_id,
  SESSION(event_time, INTERVAL '5' MINUTE)

Global windows put all events into one infinite window. Useless without a custom trigger — the window never closes on its own, so you must define when to emit results.

When to use

When you want to maintain running totals (all-time count, all-time sum) that update on every event. Requires a custom trigger to define when to emit.

Trade-off

State grows unboundedly — every event since the beginning of time is in one window. Requires careful state management and periodic state cleanup. Rarely the right choice.

SlidingFixedYesTimeRolling metrics — moving averages, rolling fraud scores

Section 05

Watermarks & Late Data

Watermarks solve the out-of-order event problem. They tell the stream processor: "I believe all events up to time T have arrived. It is safe to close windows up to T and emit results."

⚡ Event time vs processing time. Event time = when the event actually happened (the timestamp in the event). Processing time = when the event arrived at the processor. These are different — a mobile event at 10:00am might arrive at 10:45am. Always use event time for accurate analytics.

// How watermarks work

Without watermarks

You'd have to wait forever for late events before closing a window. A 10:00–11:00am tumbling window could never emit results because a late event from 10:30am might arrive at any time.

With watermarks

A watermark of "max event time seen − 5 minutes" says: if the latest event I've seen is at 11:05am, I assume all events up to 11:00am have arrived. The 10:00–11:00 window can now close and emit.

Watermark strategyHowTrade-offUse when
Bounded out-of-ordernessWatermark = max_event_time − N minutesHigher N = more late data captured, higher latencyMobile events, IoT sensors — known max lateness
Monotonically increasingWatermark = max_event_time (no delay)Any late event is dropped immediatelyEvents guaranteed to arrive in order (rare)
Custom watermarkBusiness logic determines watermark per partitionComplex to implementHeterogeneous sources with different latency profiles

// Late events — what happens when they arrive after the window closed?

Drop

Late events are silently discarded. Simplest option. Acceptable when occasional late data doesn't affect business decisions.

SimplestData loss
Side output

Late events are routed to a separate "late data" stream. Can be inspected, reprocessed, or used to trigger window updates. Best for audit purposes.

No data lossExtra stream to manage
Allowed lateness

Keep the window open for an extra N minutes after the watermark passes. Late events within this period update the result and emit a new (corrected) output. Flink supports this natively.

Most accurateDownstream must handle updates
Section 06

State Management

Stateful stream processing means the processor remembers things across events — running counts, partial aggregations, join buffers, session windows. This state must be stored, managed, and checkpointed.

// Types of state

Keyed state

State scoped to a specific key (e.g. user_id). Each key has its own isolated state. A running count of events per user — user_id=123 has its own counter, independent of user_id=456.

Types: ValueState (single value), ListState, MapState, ReducingState, AggregatingState

Operator state

State scoped to an operator instance — not to a key. Used for things like Kafka offset tracking, where one operator needs to remember all offsets it owns.

Less common. Mainly used in source and sink connectors.

// State backends — where state is stored

BackendWhere state livesPerformanceUse when
HashMapStateBackendJVM heap memoryFastestSmall state, development, testing
EmbeddedRocksDBStateBackendLocal RocksDB (on disk)Slower reads (disk)Large state that doesn't fit in memory. Production default for most jobs.
Checkpoint to S3/GCS/ADLSRemote object storeCheckpoint cost onlyDurability — state is checkpointed here for recovery, not queried from here

// Checkpointing — fault tolerance for stateful jobs

Checkpointing is Flink/Spark's mechanism for fault tolerance. The processor periodically saves a snapshot of all state to durable storage. On failure, it restarts from the last checkpoint — not from the beginning.

PropertyWhat it meansTypical value
Checkpoint intervalHow often state is snapshotted to storageEvery 30 seconds to 5 minutes. More frequent = faster recovery, more overhead.
Checkpoint timeoutHow long to wait before declaring a checkpoint failed10 minutes. If checkpoint takes longer, fail and retry.
Min pause between checkpointsMinimum time between end of one checkpoint and start of nextPrevents checkpoint overhead from dominating processing
Retained checkpointsHow many old checkpoints to keepKeep last 2-3 — allows rollback if new version has bugs
✓ Checkpointing + idempotent sink = exactly-once. If the job restarts from a checkpoint and replays some events, idempotent writes to the sink ensure those re-processed events don't cause duplicates in the output.

Section 08

Event-Driven Architecture

Event-driven architecture (EDA) is a design pattern where components communicate by producing and consuming events — rather than calling each other directly. Kafka is the most common event bus.

Publish/Subscribe — producers publish events to a topic without knowing who will consume them. Consumers subscribe to topics independently. Decouples producers from consumers completely.

Benefits

Producers and consumers are completely decoupled — adding a new consumer (e.g. fraud detection) requires zero changes to the producer. Scale consumers independently. Consumers can replay events from any point.

Challenges

No direct response — you can't "ask" for a result. Debugging is harder — trace an event across multiple consumers. Schema changes in events can break consumers silently. Need a schema registry.

✓ Real example: Order placed event → consumed by (1) inventory service, (2) notification service, (3) analytics pipeline, (4) fraud detection service. All independently. Producer (checkout service) knows nothing about any of them.

Event Sourcing — instead of storing current state in a database, store the sequence of events that produced the state. The current state is derived by replaying all events from the beginning.

Traditional approach

Store current account balance. UPDATE accounts SET balance = 500 WHERE id = 123. History is lost — you only know the current value, not how it got there.

Event Sourcing approach

Store every event: AccountOpened(£0), MoneyDeposited(£1000), MoneyWithdrawn(£500). Current balance = replay all events = £500. Complete audit trail. Can reconstruct any past state.

ProsCons
Complete audit trail — every state change recordedReplaying events gets slow as history grows
Can reconstruct state at any point in timeSnapshots needed for performance at scale
Natural fit with event-driven systems and KafkaComplex to implement correctly — eventual consistency challenges
Easy to add new projections/views of the same dataSchema evolution of past events is hard

CQRS — Command Query Responsibility Segregation — separate the write model (commands that change state) from the read model (queries that return data). Often used together with Event Sourcing.

Write side (Command)

Receives commands (PlaceOrder, CancelOrder). Validates business rules. Emits events to the event log. Optimised for writes — normalised, consistent, transactional.

Read side (Query)

Consumes events from the event log and builds read-optimised projections (materialised views, search indexes, caches). Optimised for reads — denormalised, fast, eventually consistent.

⚡ CQRS in data engineering: The write side is your operational database. The event log is Kafka. The read side is your data warehouse + BI layer. ELT IS a form of CQRS — write to operational DB, stream events to warehouse, build read-optimised models with dbt.
DimensionREST / RPC (synchronous)Event-driven (asynchronous)
Communication styleRequest → wait → responsePublish event → consumer processes independently
CouplingTight — caller knows the calleeLoose — producer knows nothing about consumers
ScalabilityCaller blocked during processingProducer not blocked — consumers scale independently
DebuggingEasy — call stack is clearHard — trace events across services
ReliabilityIf callee is down, caller failsEvents persist in Kafka — consumers process when ready
Use whenNeed immediate response (user login, payment confirmation)One event → multiple consumers, high throughput, decoupling needed
