Section 01

The Real Layers of Data Architecture

Every data system — no matter how simple or complex — moves data through a set of layers. Understanding these layers is the foundation of everything else on this page.

The 6 core layers — hover each for details
Source
Ingestion
Storage
Transform
Serving
Consume
Source

Where data originates. App databases (Postgres, MySQL), SaaS tools (Salesforce, Stripe), event streams (Kafka), files (S3, SFTP), APIs, IoT sensors.

Ingestion

Moving data from source into your system. Batch (scheduled pulls), streaming (continuous), CDC (log-based change capture). Tools: Fivetran, Airbyte, Debezium, Kafka.

Storage

Where raw and processed data lives. Data lake (S3/GCS), data warehouse (Snowflake/BigQuery), lakehouse (Delta Lake/Iceberg), vector store (Pinecone), time series DB (InfluxDB).

Transform

Cleaning, joining, aggregating, enriching. SQL transforms (dbt), large-scale processing (Spark), real-time (Flink), federated queries (Trino). Raw → clean → business-ready.

Serving

Making data accessible. Data warehouse for analysts, APIs for apps, feature store for ML models, semantic layer for BI tools. This is where data becomes useful.

Consume

The end users and systems. BI tools (Tableau, Looker), data scientists (notebooks), ML models (inference), operational apps (reverse ETL back to Salesforce).

⚠ These layers are not always separate systems. In a small startup, storage + transform + serving might all be one Snowflake account. In an enterprise, each layer might be 10 different tools. The layers are logical — not always physical.

// Pipeline vs Workflow

Data Pipeline

Focused on moving and transforming data. Source → transform → destination. Triggered by schedule or event.

e.g. Load Postgres → clean → write to Snowflake every hour

Workflow / Orchestration

Manages dependencies between tasks. Knows what runs first, handles failures, retries, alerts.

e.g. Airflow DAG: task A → task B → task C, with retry on failure

Section 02

ETL vs ELT

The biggest shift in modern data engineering. Understanding this changes how you design every pipeline.

ETL — Extract Transform Load

Transform data before loading it. Traditional approach — data warehouse must receive clean data.

Source → [Transform outside] → Warehouse
Data integrityRigidSlow to change
ELT — Extract Load Transform

Load raw data first, transform inside the warehouse. Modern approach — warehouses are powerful enough.

Source → Warehouse (raw) → [Transform inside]
FlexibleRaw data preserveddbt-friendly
✓ Why the shift to ELT? Modern warehouses (Snowflake, BigQuery) can process terabytes cheaply. Storage is nearly free. It's faster to load raw and transform later than to get transformation right before loading.

// When to use each — plain English

Use Batch when...

Daily or hourly reports are acceptable. Data arrives in bulk (nightly DB dumps, daily file drops). Team is small and prefers simple operations. Cost is a constraint — batch is cheapest. Most reporting, dashboards, and DW loads are batch.

Tools: Airflow + dbt + Spark on schedule

Use Micro-batch when...

Stakeholders need data fresher than hourly but don't actually need sub-minute latency. "Real-time dashboards" that refresh every 5-15 minutes. This covers 80% of "real-time" requirements in practice — without streaming complexity.

Tools: Spark Structured Streaming on 5-15 min intervals

Use Streaming when...

Latency under 1 minute is a hard, non-negotiable business requirement. Fraud detection (act in milliseconds or money is gone). Live inventory systems. Real-time personalization. Team has dedicated streaming expertise. Budget supports the complexity.

Tools: Kafka + Flink or Spark Streaming

Section 04

Ingestion Patterns

How data gets from source systems into your pipeline. Choosing the right pattern affects latency, cost, and complexity.

Batch

Run a bulk extract on a schedule — hourly, daily, or weekly. Pull all data (or changed data) in one job. The most common pattern in real production pipelines. Simple to build, simple to debug.

SimpleMost commonAirflow + dbt
Full Load

A type of batch — copy the entire source table every run, replacing what was there. Simple but gets expensive as tables grow. Use for small, slow-changing reference tables.

SimpleSlow at scaleSmall tables
Incremental Load

A smarter batch — only copy rows that changed since last run. Uses a watermark column (updated_at or created_at). Most efficient pattern for large tables. Does not capture deletes.

EfficientMisses deletesMost common
CDC — Change Data Capture

Read the database transaction log (WAL/binlog). Captures inserts, updates AND deletes in real time. Best when you need deletes or sub-minute latency from a database source.

Captures deletesReal-timeComplex setup
Micro-batch

Run incremental loads every few minutes instead of hourly/daily. Near real-time feel without full streaming complexity. Sweet spot for most "real-time" dashboard requirements.

Near real-timeSpark Streaming
Streaming

Events flow continuously as they happen. Sub-second latency. Required for fraud detection, live inventory, real-time personalization. 10x more complex to build and operate than batch.

Lowest latencyMost complexKafka / Flink

Most widely used pattern today. Organizes data into three layers by quality — Bronze (raw), Silver (clean), Gold (business-ready).

Lambda handles both batch (accurate, slow) and streaming (fast, approximate) by running two separate pipelines and merging results in a serving layer.

⚠ The dual codebase problem: Lambda requires maintaining the same business logic twice — once in batch code, once in streaming code. When logic changes, both must be updated. This is why many teams move to Kappa or Medallion.

Kappa simplifies Lambda by eliminating the batch layer entirely. Everything is streaming. Historical reprocessing is done by replaying the event log.

When Kappa works

Event log retained long-term (Kafka). Business logic is the same for batch and stream. Team has streaming expertise.

When Kappa fails

Need complex historical joins. Reprocessing is expensive. Team is small — streaming adds significant ops burden.

// The golden rule — transform as late as possible

Anti-pattern

Transform before loading (ETL). You lose the raw data. If business logic changes, you have to re-extract from source. Transformation bugs corrupt your only copy.

Modern pattern (ELT)

Load raw first, transform inside the warehouse/lake. Raw data is always preserved in Bronze. You can re-run transforms any time. Business logic changes don't require re-ingestion.

✓ dbt for most things. If your data fits in a cloud warehouse (Snowflake/BigQuery/Redshift) and your transforms are SQL — use dbt. It handles 90% of real-world transform needs with the best developer experience. Only reach for Spark when dbt genuinely can't handle the scale or complexity.
Section 07b

Data Mesh & Data Fabric

These are often confused. They solve different problems — one is an organisational model, the other is a technology layer.

Data Mesh is a decentralised approach where domain teams (Sales, Finance, Marketing, Product) own their data end-to-end — ingestion, storage, transformation, and serving. There is no central data team as a bottleneck.

// The 4 principles of Data Mesh

1. Domain Ownership

Each business domain owns its data pipeline end-to-end. The Sales team owns the sales data product. They build it, maintain it, and are accountable for its quality. No central team is a middleman.

2. Data as a Product

Each domain treats its data output as a product — with an owner, documentation, SLAs, and quality standards. Other teams are the consumers. The domain team is responsible for keeping the product useful.

3. Self-serve Platform

A central platform team (not data team) provides the infrastructure — storage, compute, orchestration, governance tooling — so domain teams can build pipelines without needing platform engineering skills.

4. Federated Governance

Global standards (naming conventions, PII rules, SLA expectations) are set centrally. Domain teams apply them locally. Governance without centralisation. Think "federal law + local implementation."

When Mesh works

Large org (50+ engineers). Multiple autonomous domain teams. Central data team is a bottleneck. Domains have different data needs and cadences. Leadership buy-in for org change.

When Mesh fails

Small team — overhead kills productivity. Domain teams lack data engineering skills. No self-serve platform exists yet. Organisation isn't structured around clear domains. Mesh is an org transformation, not just a tech choice.

Data Fabric is a technology architecture — an active metadata layer that automatically connects, integrates, and governs data across all your systems regardless of where it lives.

💡 If Data Mesh asks "who owns the data?", Data Fabric asks "how do we make all data accessible everywhere automatically?"

// What Data Fabric does

Active Metadata

Continuously scans all data sources, automatically discovers schemas, relationships, and data lineage. Metadata drives decisions — e.g. automatically classifying PII, suggesting joins.

Unified Access Layer

One query interface across data warehouse, data lake, operational databases, and SaaS tools. Users don't need to know where data physically lives.

Automated Integration

ML-powered recommendations for how to join, transform, and integrate data. Reduces manual pipeline development. Learns from usage patterns.

Intelligent Governance

Automatic PII detection, policy enforcement, access control across all systems. One governance policy applied everywhere without manual configuration per system.

Section 08 — New

The AI Layer

Modern data architectures now include a dedicated AI layer that didn't exist 3 years ago. It sits between your transform layer and your serving layer — turning processed data into intelligence.

Where the AI layer fits
Feature Store

Stores ML features — pre-computed, versioned, and shared across models. Solves the "training-serving skew" problem where features computed differently at train vs inference time. Tools: Feast, Tecton, Vertex Feature Store, Hopsworks.

Use when: multiple ML models share the same features, or you need consistent features at training and inference time.

Vector Store

Stores embedding vectors — numerical representations of text, images, or any data. Enables semantic search (find similar, not just exact), RAG pipelines, and recommendation systems. Tools: Pinecone, Weaviate, Qdrant, pgvector, Chroma.

Use when: building LLM applications, semantic search, or any AI feature that needs to find "similar" data.

Model Registry

Tracks trained models, experiments, hyperparameters, and performance metrics. Version control for ML models. Enables rollback, A/B testing, and audit trails. Tools: MLflow, Weights & Biases, SageMaker Model Registry.

Use when: you have more than one ML model in production or need to track experiments systematically.

RAG Pipeline

Retrieval-Augmented Generation — connect your private data to LLMs. Documents → chunk → embed → vector store → at query time, retrieve relevant chunks → pass to LLM with context. Tools: LangChain, LlamaIndex, custom pipelines.

Use when: building internal chatbots, document Q&A, or any LLM app that needs your company's private data.

// Unstructured data → structured insight pipeline

One of the most common new data engineering problems: you have PDFs, emails, call recordings, or images that contain valuable information but aren't structured. The AI layer solves this.

Section 07

Pipeline Design Principles

What separates a pipeline that works once from a pipeline that works in production forever.

01
Idempotency

Running the same pipeline twice should produce the same result as running it once. If your pipeline re-runs, it should not create duplicates or corrupt data.

-- Idempotent write: DELETE + INSERT instead of just INSERT
DELETE FROM fact_sales WHERE date_id = '2024-01-01';
INSERT INTO fact_sales SELECT * FROM staging_sales
WHERE date_id = '2024-01-01';
02
Backfilling

Backfilling means re-running a pipeline for historical dates — when you fix a bug, add a new column, or onboard a new data source. Design pipelines to accept a date parameter from day one.

-- Parameterized pipeline (Airflow example)
def run_pipeline(execution_date):
    load_data(start=execution_date, end=execution_date + timedelta(days=1))
    transform(date=execution_date)
    write(partition=execution_date)
03
Late Arriving Data

5-15% of mobile events arrive late. Your pipeline must decide: wait for late data (higher latency) or process and correct later (more complex).

StrategyHowBest for
Grace periodWait N hours before closing a windowBatch pipelines
WatermarksTrack max event time, allow N minutes lateStreaming (Flink/Spark)
Append + reprocessAccept late data, rerun affected partitionsWhen accuracy matters more than latency
04
Deduplication

At-least-once delivery guarantees mean duplicates are normal. Design for it at every layer.

-- Deduplicate with ROW_NUMBER pattern
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY event_id
    ORDER BY received_at DESC
  ) AS rn
  FROM raw_events
) WHERE rn = 1
05
Error Handling & Retries

Every pipeline will fail. Design for it: exponential backoff retries, dead letter queues for poison records, alerting on repeated failures.

Error typeStrategy
Transient (network timeout)Retry with exponential backoff (1s, 2s, 4s, 8s)
Poison record (bad data)Dead letter queue — skip and investigate
Schema mismatchAlert immediately — stop pipeline, don't corrupt data
Downstream not readySensor — wait and check every N minutes
Section 08

Data Contracts

A data contract is a formal agreement between data producers and consumers about the shape, quality, and SLA of data. Shifts failure detection from runtime to deployment time.

Without contracts

Source team renames a column → your pipeline breaks at 3am → dashboards show wrong numbers → you find out from a Slack message from an angry analyst.

With contracts

Source team tries to rename a column → schema registry rejects the change as a breaking change → PR is blocked → you're notified before deployment.

// What a contract defines

ElementExample
SchemaFields, types, nullable or not
SemanticsWhat does user_id mean? Is it always populated?
SLAData available by 6am UTC daily
Quality rulesrevenue > 0, customer_id never null
Evolution rulesAdding fields OK, renaming fields BREAKING

// Schema formats

Avro

JSON-based schema. Most common with Kafka. Schema stored in Schema Registry. Binary serialization — compact.

Protobuf

Google's format. Strongly typed. More compact than Avro. Common in microservices and gRPC pipelines.

Section 09

Monitoring & Observability

Two different things. Both are required in production.

Pipeline Monitoring

Did it run? Did it finish on time? Did tasks fail? How long did it take?

Tools: Airflow UI, Dagster, CloudWatch, Datadog

Data Monitoring

Did it run correctly? Are row counts normal? Are there nulls where there shouldn't be? Did revenue drop 90%?

Tools: dbt tests, Great Expectations, Monte Carlo

// The three pillars of DE monitoring

PillarWhat to monitorAlert when
FreshnessWhen was the table last updated?Table not updated within SLA window
VolumeHow many rows were loaded?Row count drops/spikes >20% vs yesterday
QualityNull rates, duplicate rates, value distributionsNull rate on key column exceeds threshold

// SLAs vs SLOs

SLA — Service Level Agreement

The external commitment: "Sales dashboard will be updated by 8am every day." Breach = business impact.

SLO — Service Level Objective

The internal target: "Pipeline must complete by 7am to meet the 8am SLA." Your engineering target with buffer.

Orchestration Deep Dive

Orchestration is the layer that manages task dependencies, scheduling, retries, and alerts across your entire pipeline. Without it, you're running cron jobs and praying.

💡 A pipeline moves data. An orchestrator makes sure the pipeline runs in the right order, at the right time, with the right dependencies — and tells you when it doesn't.

// Key concepts

ConceptWhat it meansExample
DAGDirected Acyclic Graph — tasks with dependencies, no cycles allowedTask A must finish before Task B starts. Task B and C run in parallel. Task D waits for both B and C.
TaskA single unit of work in the DAGRun a dbt model, execute a SQL query, trigger a Spark job, call an API
SensorWait for a condition before proceedingWait for S3 file to exist. Wait for upstream table to be updated. Wait for API to respond.
RetryRe-run a failed task automaticallyRetry 3 times with exponential backoff (1 min, 2 min, 4 min). Alert after all retries exhausted.
SLAAlert if task hasn't completed by a deadlinePipeline must finish by 7am. If not, send Slack alert at 7:05am before analysts start work at 8am.
BackfillRe-run pipeline for historical datesBug was in production for 2 weeks — re-run all daily runs from Jan 1 to Jan 14 to fix the data.
IdempotencyRunning the same task twice gives the same resultRequired for safe retries and backfills. DELETE + INSERT pattern instead of just INSERT.
XComPass values between tasks in a DAGTask A extracts a record count → passes it to Task B which alerts if count is below threshold.

// Orchestration tools — compared

Apache Airflow

The industry standard. DAGs defined in Python. Huge ecosystem of operators (Spark, dbt, BigQuery, S3, Slack...). Battle-tested at thousands of companies. Managed options: MWAA (AWS), Cloud Composer (GCP), Astronomer.

Industry standardHuge ecosystemComplex setupPython-only DAGs
When to use Airflow

Your company already uses it. You need the broadest ecosystem support. You're comfortable with Python-defined DAGs. Team has Airflow experience. Large number of complex, interdependent pipelines.

⚠ Airflow was designed for task orchestration, not data-aware orchestration. It doesn't understand data assets, only task success/failure.

Dagster

Asset-oriented orchestration. You define data assets (tables, files, ML models), not just tasks. Dagster knows what data was produced, when, and by what. Built-in data lineage, observability, and software-defined assets.

Asset-awareBest observabilityModern designSmaller ecosystem
When to use Dagster

Greenfield projects. Teams that care about data lineage and asset tracking. dbt + Dagster is a very powerful combo. When you want orchestration that understands what data was produced, not just whether a task ran.

Dagster Cloud is managed. Dagster Open Source is self-hosted.

Prefect

Python-first. Your Python functions become tasks and flows with minimal decoration. Easiest to get started with. Strong dynamic workflows — generate tasks at runtime based on data. Prefect Cloud is managed.

Easiest to startDynamic workflowsPython-nativeLess mature than Airflow
When to use Prefect

Small to medium teams that want to move fast. Workflows that are highly dynamic (number of tasks changes based on data). Teams that want managed infrastructure without Airflow's operational overhead.

Temporal

Durable execution platform — not just for data pipelines. Workflows that can run for days or months, survive server restarts, and handle complex retry logic. More general than Airflow — used for both data and application workflows.

Durable executionAny languageNot data-specificSteeper learning curve
When to use Temporal

Long-running workflows (hours/days). When you need workflow state to survive infrastructure failures. When you need orchestration across both data pipelines AND application logic. Used by Stripe, Netflix, Airbnb.

Data Governance & Catalog

At scale, nobody knows what tables exist, who owns them, where they came from, or whether they can be trusted. Governance is the system that answers those questions.

// The 3 pillars

Data Catalog

What data exists? A searchable inventory of all datasets, tables, columns, and their descriptions. Analysts can find data without asking engineers. Think of it as Google for your internal data.

Tools: DataHub, Amundsen, Apache Atlas, Google Dataplex, Alation

Data Lineage

Where did this data come from? Track the full journey: source DB → Bronze → dbt model → Gold table → dashboard. When a source changes, you instantly know what downstream tables and reports are affected.

Tools: dbt (built-in), DataHub, OpenLineage, Marquez

Data Quality

Can I trust this data? Automated checks that run after every pipeline run — null rates, duplicate rates, value range checks, referential integrity. Catch data quality issues before analysts do.

Tools: dbt tests, Great Expectations, Soda, Monte Carlo

Section 14 — New

Security & Access Control

Data security is an architectural concern — not something you bolt on later. The decisions you make about how data flows through your layers determine what's possible to secure.

// Core access control patterns

Row-Level Security (RLS)

Users only see rows they're allowed to see. A sales rep sees only their own customers. A regional manager sees their region. Implemented at the warehouse or BI layer — same table, different views per user.

Supported in: Snowflake, BigQuery, Redshift, dbt + BI tools

Column Masking / Encryption

PII columns (email, SSN, phone) are masked for users without the right role. Analysts see john.d***@gmail.com. Data engineers see the real value. Masking is applied dynamically at query time.

Supported in: Snowflake Dynamic Data Masking, BigQuery column-level security

Role-Based Access Control (RBAC)

Grant permissions to roles, not individual users. Analysts role gets SELECT on Gold layer only. Engineers role gets write access to Bronze and Silver. Admins get everything. Users inherit permissions from their role.

Tokenisation

Replace sensitive values with non-reversible tokens before storing. The original credit card number never enters your data warehouse — only a token that can be looked up in a secure vault if needed.

Section 15 — New

Cost Optimization

Cloud data platforms can get expensive fast. Most cost problems come from a handful of anti-patterns that are easy to fix once you know them.

// Storage optimization

TechniqueWhat it doesSaving
PartitioningSplit tables by date/region so queries only scan relevant partitions. A query for Jan data scans only Jan partition, not the full table.50-95% scan reduction for time-filtered queries
Clustering / Z-orderingCo-locate rows with similar values on disk. BigQuery clustering, Snowflake clustering keys, Delta Lake Z-ORDER.20-80% scan reduction for filtered queries
Columnar formatsStore data in Parquet or ORC instead of CSV/JSON. Columnar reads only the columns needed — not the whole row.5-10x smaller storage, faster reads
Storage tiersMove old data to cheaper storage. S3 Glacier for data >1 year. Snowflake time travel retention tuning.70-90% cost reduction for cold data
CompressionZSTD or Snappy compression on Parquet files. Warehouses do this automatically — but verify it's on.3-5x storage reduction

// Compute anti-patterns — most expensive mistakes

#Anti-patternWhy it's expensiveFix
1SELECT * on large tablesScans all columns even if you need 3. In columnar DBs, costs scale with columns scanned.Always select only needed columns
2Full table scans without partition filterScans 3 years of data to get last 7 daysAlways filter on partition column in WHERE clause
3Cartesian joins (missing JOIN condition)1M rows × 1M rows = 1 trillion row result. Cluster dies, bill explodes.Always verify JOIN keys. Use EXPLAIN to check join type.
4Idle warehouses / clustersSnowflake warehouse running at full size 24/7 with no queriesAuto-suspend after 1-5 min inactivity. Auto-scale down.
5Wrong warehouse size for workloadXL warehouse for a query that runs fine on SStart small. Scale up only when proven necessary.
6Materialising everythingdbt model materialised as table rebuilds fully every run — expensive for large modelsUse incremental materialisation for large models
7Redundant data copiesSame data in lake + warehouse + 3 different schemas "just in case"Single source of truth per layer. Delete unused tables.
✓ The biggest cost wins, in order: (1) partition your largest tables, (2) auto-suspend idle warehouses, (3) delete unused tables and schemas, (4) switch SELECT * to SELECT specific columns. These four changes typically cut warehouse costs by 40-60% in most orgs.
