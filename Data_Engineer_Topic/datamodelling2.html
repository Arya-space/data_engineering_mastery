Schema Types

Once you know your grain and whether it's OLAP or OLTP, you choose a schema type. Click each one to explore its structure, trade-offs, and when to use it.

Star Schema
Fact table at the center. Flat dimension tables surrounding it. The most common analytical schema.
Fastest queries Easy to understand Some redundancy OLAP
Designed by
Ralph Kimball
Schema shape
1 fact + N flat dims
Join depth
One join per dimension
Best warehouse
Snowflake, BigQuery

When to use:

  • System is designed for analytics and reporting
  • Analysts and BI tools (Tableau, Looker) will query it
  • Dimensions are flat — no deep hierarchies
  • Query speed matters more than storage
✓ Go-to schema for most data warehouses. Simple, fast, and analysts can understand it without a data engineer's help.

3NF — Inmon Model
Fully normalized Enterprise Data Warehouse. Single source of truth. Build data marts on top for analytics.
No redundancy Single source of truth Complex joins Slower analytics OLTP / EDW
Designed by
Bill Inmon
Schema shape
Fully normalized tables
Flow
EDW → Data Marts
Best for
Enterprise DW, OLTP

When to use:

  • System is transactional — frequent inserts/updates
  • Data integrity is critical
  • Need a single enterprise source of truth
  • Will build separate data marts for each team
💡 Inmon builds the EDW first (normalized), then creates denormalized data marts per business unit. Opposite of Kimball's bottom-up approach.

One Big Table (OBT)
Denormalize everything into a single wide table. Zero joins for analysts. Popular with columnar warehouses.
Simplest for analysts No joins needed Huge storage Hard to change OLAP
Schema shape
1 wide flat table
Joins needed
None
Storage cost
Very high
Best for
Simple reporting, small teams

When to use:

  • Small team, analysts prefer simplicity over structure
  • Using columnar stores (BigQuery, DuckDB, Snowflake)
  • Data doesn't change much
  • Performance-critical workloads on a fixed query pattern
⚠ OBT is an anti-pattern at scale. If business logic changes, you have to rebuild the whole table. Use sparingly.

Data Vault 2.0
Three building blocks: Hubs (business keys), Links (relationships), Satellites (attributes + history). Built for auditability and change.
Full audit trail Easy to add sources Complex to build Hard to query directly Enterprise
Hubs
Unique business keys
Links
Relationships between hubs
Satellites
Attributes + history
Best for
Regulated industries, audit

When to use:

  • Need full audit trail of every data change
  • Multiple source systems feed the same entities
  • Regulated industry (finance, healthcare, insurance)
  • Data changes frequently and history must be preserved
⚡ Data Vault is the raw layer. You still build a Star Schema on top for analysts to query — Vault is the foundation, not the end state.
