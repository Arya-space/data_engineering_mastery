Section 01

What is Architecture Design?

Data architecture design is the process of choosing how data flows through your system — which tools handle ingestion, where data is stored, how it's transformed, who serves it, and how it's governed. A bad architecture decision made early is expensive to undo.

💡 Architecture is not about picking the newest or most impressive tools. It is about picking the simplest combination that solves your actual problem at your actual scale, with your actual team. Complexity is a liability, not a feature.

// Why this matters

Wrong architecture = technical debt

A 3-person startup that builds a full Lambda architecture in year 1 will spend 80% of engineering time on ops instead of features. The complexity doesn't match the scale — and you can't hire your way out of it.

Right architecture = leverage

The right choice compounds over time. Medallion + dbt + Snowflake chosen correctly in year 1 can scale to hundreds of models and dozens of engineers with minimal re-architecture. Simple beats clever.

Architecture is not permanent

Every company evolves. Startups outgrow simple stacks. Enterprises decompose monoliths. Design for the next 18–24 months, not forever. Use open formats (Iceberg, Parquet) to avoid lock-in.

// What the different architecture types actually mean

TypeWhat it actually isCommon confusion
Data Warehouse designYour storage + transform layer uses structured, schema-on-write data. Star schema, Kimball, facts and dimensions. Optimised for SQL analytics.People think "DW design" means only Snowflake or BigQuery. It's a philosophy — schema-on-write, structured, BI-optimised.
Data Lake designRaw files in object storage (S3/GCS). Any format, any structure. Schema-on-read. Cheap. Good for ML and exploration.A lake without governance becomes a swamp. You need a catalog and quality layer on top.
Data Pipeline designHow data MOVES between layers — batch, streaming, CDC. The plumbing that connects source to destination.The pipeline IS the architecture for many people. It's actually just one layer of it.
Data Mesh designWho OWNS the layers — not a technology. Each domain team owns their data product end-to-end.Mesh is an org model, not a tool. You can't buy Data Mesh. You have to reorganise your teams.
Data Fabric designA metadata-driven technology layer that automatically connects, integrates, and governs data across all systems.Fabric is a tech architecture. Mesh is an org model. They can coexist — Fabric can be the platform that enables Mesh.

The designer works in two phases: requirements gathering (6 questions) and stack generation (the rules engine produces your architecture). Here is exactly what each question does and why it's asked in this order.

StepQuestionWhy firstWhat it eliminates

Stack layers

Every layer is shown in order — source to consumption. Each entry shows the layer name, the specific tool for your cloud and team size, and the reason that tool was selected over alternatives.

Why-not section

The most useful part for interviews and stakeholder discussions. Every major tool or pattern that was eliminated has an explicit explanation — not just "we didn't pick it" but "here's why it doesn't fit your specific situation."

Section 03

The Rules Engine

The designer is driven by 10 rules that run in sequence. Each rule takes your answers as input and either eliminates options, selects tools, or adds layers. Earlier rules have higher priority and can override later ones.

⚡ Rules 1, 2, and 3 are hard filters — they eliminate entire categories before any tool names are chosen. Rules 4–7 fill in specific tools. Rules 8–10 add compliance, scale, and the why-not library on top.
Rule 01 — Hard filter (highest priority)
Data type eliminates entire storage categories

Before anything else, the data type rules out entire classes of storage and processing tools. This cannot be overridden by any later rule.

IF data_type = time_seriesTHEN storage = TimescaleDB / InfluxDB / QuestDBELIMINATE standard DW as primary
IF data_type = media (images/video/audio)THEN storage = object_store (S3/GCS/ADLS)ELIMINATE DW — only for metadata output
IF data_type = documents/PDFsTHEN storage = object_store + vector_storeTHEN ai_layer = required
IF data_type = structured OR semi_structuredTHEN storage = DW or Lakehouse (standard path)
IF data_type = mixed/multimodalTHEN storage = lake as landing zone + route by typeTHEN pattern = Medallion (forced)
Rule 02 — Hard filter
Latency forces the ingestion pattern and processing mode

Latency is the second hardest constraint. It determines how data enters your system and eliminates architecture patterns that cannot meet the requirement.

IF latency = daily/hourlyTHEN ingestion = batch (Fivetran / Airbyte / dbt)ELIMINATE Kappa architecture
IF latency = 5–15 minutesTHEN ingestion = micro-batch (Spark Structured Streaming)ELIMINATE full streaming overhead
IF latency = under 1 minuteTHEN ingestion = streaming (Kafka / Kinesis / Pub/Sub)THEN processing = Flink / Spark StreamingELIMINATE batch-only stacks
IF latency = sub-secondTHEN ingestion = streaming + in-memory serving (Redis)ELIMINATE DW in the hot path
Rule 03 — Pattern selection
Architecture pattern defines the overall layer structure

Once data type and latency are set, the pattern determines how layers are organised. Some patterns are incompatible with certain latency requirements or team sizes — the engine rejects them.

IF pattern = MedallionTHEN layers = Bronze → Silver → GoldTHEN transform = dbt (SQL-first)
IF pattern = LambdaTHEN layers = batch_path + speed_path + serving_mergeWARNING: same business logic written twice
IF pattern = KappaTHEN layers = event_log + stream_processor + servingREQUIRE latency = streaming (Rule 02)REQUIRE event log retention ≥ 30 days
IF pattern = Data MeshTHEN add domain_ownership + self_serve_platform layersREQUIRE team_size = enterprise (50+ engineers)
IF pattern = autoTHEN pick = Medallion (batch/micro-batch) OR Lambda (streaming) based on Rule 02

Rule 05 — Complexity filter
Team size swaps managed tools for self-hosted tools

The same logical layer gets different tools depending on team size. A startup should never self-host Kafka. An enterprise may prefer OSS to avoid vendor lock-in at scale.

IF team = startup (1–3 DEs)THEN all tools = managed/SaaS onlyELIMINATE self-hosted Kafka, Flink, Airflow, Spark
IF team = mid-size (5–15 DEs)THEN ingest = managed, transform = dbt + Spark, orchestration = managed Airflow
IF team = enterprise (50+ DEs)THEN self-hosted = acceptableTHEN governance = mandatoryTHEN data_mesh = possible
Rule 06 — Additive layer
AI need adds Feature Store and/or Vector Store on top

The AI layer is additive — it does not replace any existing layer. It sits between transform and serving. If not needed, it is skipped entirely to keep the stack minimal.

IF ai_need = ML modelsTHEN add feature_store (cloud-specific)THEN add model_registry (MLflow or managed)
IF ai_need = LLM/RAGTHEN add vector_store (cloud-specific)THEN add embedding_pipeline (LangChain / LlamaIndex)
IF ai_need = noneTHEN skip AI layer entirely
Rule 07 — Override rule
Snowflake and Databricks are cloud-agnostic overrides

Snowflake and Databricks run on all three major clouds. If selected, they replace the cloud-native warehouse from Rule 04 — but all other cloud-specific tools remain unchanged.

IF warehouse_override = SnowflakeTHEN warehouse = Snowflake (replaces Redshift / BigQuery / Synapse)THEN table_format = Iceberg
IF warehouse_override = DatabricksTHEN warehouse + transform = Databricks LakehouseTHEN table_format = Delta LakeTHEN dbt runs on Databricks SQL
Rule 08 — Compliance overlay
Regulated industries add mandatory security and governance requirements

Healthcare (HIPAA), finance (SOX, PCI-DSS), and EU companies (GDPR) have non-negotiable requirements that layer on top of the base stack.

IF compliance = HIPAATHEN encryption = at-rest + in-transit (mandatory)THEN audit_log = all data accessELIMINATE any tool without BAA
IF compliance = GDPRTHEN PII = masked at Bronze OR separate vaultTHEN data_residency = EU region onlyTHEN design for right_to_erasure
IF compliance = PCI-DSSTHEN card_data = tokenise before pipelineTHEN network = isolated VPC / private endpoints
Rule 09 — Scale check
Data volume changes the transform and storage tier

Volume estimates change which specific tools are appropriate. A 1 GB/day pipeline and a 1 TB/day pipeline both use dbt — but very different infrastructure behind it.

IF volume < 100 GB/dayTHEN transform = dbt on warehouse only (no Spark needed)
IF volume = 100 GB – 10 TB/dayTHEN transform = dbt + Spark for heavy modelsTHEN partitioning = mandatory
IF volume > 10 TB/dayTHEN transform = Spark / Flink primaryTHEN storage = Lakehouse (lake-first)WARN: dbt alone too slow for raw layer at this scale
Rule 10 — Why-not library
Every rejected option gets an explicit explanation

The output always includes what you did NOT choose and why. This is the most valuable part for interviews and architectural discussions — reasoning, not just recommendations.

IF Kafka eliminatedWHY NOT: Your latency is batch/hourly. Kafka adds broker management, partition tuning, and consumer group complexity with zero latency benefit when you don't need sub-minute freshness.
IF Lambda eliminatedWHY NOT: Lambda requires maintaining the same business logic twice — batch code and streaming code. Every logic change must be applied to both. Medallion achieves your goals with a single codebase.
IF Data Mesh eliminatedWHY NOT: Mesh requires autonomous domain teams with data engineering skills, a self-serve platform, and federated governance. At your team size, the overhead of domain ownership outweighs the benefits.
IF self-hosted Airflow eliminatedWHY NOT: A small team cannot afford to spend 30%+ of their time on Airflow infrastructure. Use a managed option and spend that time building data products instead.
