Section 01

What is a Slowly Changing Dimension?

Imagine you store employee data in a database. Most days nothing changes — but occasionally an employee moves city, gets promoted, or changes their name. These changes happen slowly, but they do happen.

The question every data engineer must answer: what do you do when a row changes?

💡 Real example: Chris is an Owner on January 1st. On January 2nd, Chris becomes a Manager. Do you overwrite the old record, or keep both?

// The two approaches

SCD Type 1 Overwrites history

Delete the old value. Replace with the new one. Simple — but history is gone forever.

⚠ "Owner" is gone. No way to know Chris was ever an Owner.

Section 02

DDL — Designing the Table

The magic of SCD Type 2 is in the columns you add to a normal table. Here is how you design it.

// Basic SCD Type 2 table

CREATE TABLE customer_dim (

    -- natural key (not unique — same customer has multiple rows)
    customer_id      INT,

    -- your actual business data
    name             VARCHAR(100),
    city             VARCHAR(100),

    -- SCD Type 2 tracking columns ← the key design decision
    effective_date   DATE,          -- when this version became active
    end_date         DATE,          -- when this version expired (null = still active)
    is_current       INT,           -- 1 = active, 0 = historical

    -- surrogate key: unique per row, even if same customer
    sk               VARCHAR(64)    -- usually an MD5/SHA hash
);
💡 The 9999-12-31 trick: Instead of using NULL for end_date on active records, many engineers use 9999-12-31 as a "no end date" sentinel. This makes date comparisons easier — you can always do end_date > @date without null-checking.

// The three SCD Type 2 columns explained

ColumnPurposeActive RecordHistorical Record
effective_dateWhen this version started2024-01-022024-01-01
end_dateWhen this version endedNULL or 9999-12-312024-01-02
is_currentQuick flag for current row10

// Surrogate key (SK)

The natural key (customer_id) is no longer unique — the same customer has multiple rows. So we generate a surrogate key: a hash of the natural key + effective date, guaranteeing uniqueness per version.

-- Example SK generation in SQL
SELECT MD5(customer_id || '-' || effective_date) AS sk,
       customer_id, name, city, effective_date, end_date
FROM customer_dim;
Section 03

DML — Loading & Updating Data

Designing the table is step one. Step two is actually loading changes into it. Here is the full DML lifecycle.

When a record first arrives, insert it as the active version.

-- First time we see customer 5
INSERT INTO customer_dim
    (customer_id, name, city, effective_date, end_date, is_current)
VALUES
    (5, 'Chris', 'Amsterdam', '2024-01-01', '9999-12-31', 1);

When a change arrives, expire the old row first, then insert the new version.

-- Step 1: expire the old record
UPDATE customer_dim
SET   end_date   = '2024-01-02',
      is_current = 0
WHERE customer_id = 5
  AND is_current  = 1;

-- Step 2: insert the new active record
INSERT INTO customer_dim
    (customer_id, name, city, effective_date, end_date, is_current)
VALUES
    (5, 'Chris', 'Paris', '2024-01-02', '9999-12-31', 1);
⚠ Always expire first, then insert. If you do it the other way, you briefly have two active rows for the same customer.

Section 04

Querying SCD Type 2

The most common SCD query: get the version of a record that was active at a specific point in time.

-- Get the record valid at a specific date
SELECT customer_id, name, city, effective_date, end_date
FROM   customer_dim
WHERE  effective_date <= '2024-03-01'   -- started on or before our date
  AND  end_date       >  '2024-03-01'   -- not yet expired on our date
ORDER BY customer_id;
🧠 Why both conditions?
effective_date <= @date — the record had already started.
end_date > @date — the record had not yet ended. 
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.getOrCreate()
query_date = "2024-03-01"

result = customer_dim \
    .filter(
        (col("effective_date") <= query_date) &   # ← brackets required!
        (col("end_date")       >  query_date)
    ) \
    .select("customer_id", "name", "city", "effective_date", "end_date") \
    .orderBy("customer_id")

result.show()
⚠ Common bug: In PySpark, every condition in .filter() must be wrapped in its own parentheses when using &. Missing brackets causes a silent logic error.
import pandas as pd

query_date = pd.Timestamp("2024-03-01")

result = customer_dim[
    (customer_dim["effective_date"] <= query_date) &
    (customer_dim["end_date"]       >  query_date)
][["customer_id", "name", "city", "effective_date", "end_date"]] \
 .sort_values("customer_id")

print(result)

Where Does SCD Fit in the Pipeline?

SCD Type 2 tables live in the Silver / Dimension layer of a modern data stack — after raw ingestion, before analytics.

// Batch pipeline

Source
→
Ingestion
→

// Streaming pipeline

Source
→
CDC
→
Message Queue
→
Stream Processor → SCD Type 2
→
Serving / Gold
💡 Batch vs Streaming: Most companies use batch (daily/hourly runs). Streaming is only needed when you need changes reflected in minutes or seconds — it's significantly more complex.
